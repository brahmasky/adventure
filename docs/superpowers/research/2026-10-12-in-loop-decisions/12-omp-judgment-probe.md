## 0. Core architecture [READ]
- Wire client: AI/src/judgment/typesafe.ts. `TypeSafeJudge.judge()` POSTs `{state, model, questions}` to `{base}/v1/systemone` (typesafe.ts:36-39,123-124). Same shape as Houge's Jev front door (state + typed questions).
- Question types (AI/src/judgment/types.ts:23-74): `choice` (answer: choice, probabilities per option, confidence), `noul` (yes-prob 0-1, optional true/false criteria), `score` (weighted level index, probabilities, confidence). All questions in one request share one state.
- Orchestration: CA/src/judgment/index.ts `ChainJudge` walks the `judge` model-role chain. Default chain CA/src/priority.json:99-105 = `typesafe/jev-latest`, `openrouter/~typesafe/jev-latest`, `@tiny`, `@smol`, `@default`. index.ts:193-198: from the first native (TypeSafe) candidate on, ONLY native candidates remain, so a chat model never stands in for a failed jev. If there is no native candidate, a prompted chat model (TextJudge keyword prompts, AI/src/judgment/text*.ts) or on-device model answers instead, and the session model is appended as last resort (index.ts:165-172, `withSessionFallback`).
- Failure handling: transient 408/429/5xx retried, max 3 attempts, backoff 500ms*2^n capped 5s, honours retry-after (typesafe.ts:81-84,93-98,178-180). Per-attempt timeout 10s (typesafe.ts:81). 401/402/403 => candidate skipped for 5 min (index.ts:136,279-280). Chain rebuilt/cached 1s (index.ts:144). Every caller wraps its own shorter deadline and degrades (below).
- Answer cache: `sharedJudgmentCache()` (CA/src/judgment/cache.ts, sqlite at getJudgmentCacheDbPath), per-question hits skip the network (index.ts:419-428) [READ]; where the db lives not checked.
- Cost/ledger: each billed attempt -> `onUsage` -> `appendModelUsage` writes a `model_usage` session entry (purpose, role, api, provider, model, usage, stopReason, errorMessage) (CA/src/session/session-entries.ts:83-94; session-manager.ts:3285-3305), plus one OTel `judgment` span if telemetry on (pi-agent-core/src/telemetry.ts:1713-1750). Neither records the question text or the answer/probability.

### "unexpected-stop" vs mu turn.continue/turn.completion
[INFER, mu source not read]: unexpected-stop is the one omp point that resembles mu's continue-decision: a single yes/no (`noul`) on the last assistant text only, threshold 0.5, nudges the model back via a hidden developer message, max 3 retries. It is narrower than a completion judge: it never asks "is the task done", sees no tool results/todos/goal, and is skipped entirely for turns with a tool call (isUnexpectedStopCandidate, classifier.ts:46-65). Default mode is `mechanical` (below), which does NOT call the judge.

## 7. omp `todo` tool
- CA/src/tools/todo.ts. Ops: init, start, done, rm, drop, block, unblock, append, view (schema todo.ts:55-70). State = phases `[{name, tasks:[{content,status,blocker?}]}]`, status pending|in_progress|completed|abandoned|blocked; at most one in_progress (normalizeInProgressTask). Held in session (`getTodoPhases`) and persisted on the branch through each todo toolResult `details.phases` (committedTodoPhases, todo.ts:23-45).
- Settings: `todo.enabled` default true, `todo.reminders` true, `todo.remindersMax` 3, `todo.eager` default (tools/settings.ts:347-395).
- Visibility: (a) RPC `get_state` returns `todoPhases` (rpc-types.ts:187); (b) RPC command `set_todos` lets the host replace phases (rpc-types.ts:66, rpc-mode.ts:2126); (c) the model's `todo` calls are ordinary tool_call/tool_result events, so Houge's extension hooks see args and details; (d) `todo_reminder` event (todos, attempt, maxAttempts) when the agent stops with pending/in_progress items; the tracker then injects a developer system-reminder and continues, up to 3 times (todo-tracker.ts:215-285). This is a mechanical (non-LLM) "not done yet" nudge.
- Houge currently launches with `--tools read,edit,write`, so `todo` is not in the active tool set [INFER from tools/index.ts:629-640; verify with RPC get_state dumpTools]; the reminder path is then dormant because phases are empty (todo-tracker.ts:225-229).
