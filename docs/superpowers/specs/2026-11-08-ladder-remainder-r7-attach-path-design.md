## 4. The entry

### 4.0 The recording rule (ADR 0034 §3.2, adapted to the settle stage and to delivery)
`attach.path` is the first entry consulted **after** the turn's end signal. R5/R6's guard (`!turn.endSignalled`, `!i.signal.aborted`) cannot be its liveness rule (§3). The rule this slice states, and the ADR 3.2 sentence it drafts (Decision 2):

- **Parse (E2).** "Live" at the settle stage means the turn took `settle()`'s success arm: `!turn.failure` at `:906`. A failed, aborted, killed or crashed turn takes `finishFailure` and is never consulted, so it writes no row. The rows are written in `finishSuccess` with the turn's own terminal records (`outcome.complete`, `recordChatTurn`), on the consulting `Turn` passed in (never `this.turn`), `run_id` = `t.req.run_id`, `tool_call_id` null. **Residual, stated:** `finishRun`'s CAS in `ompComplete` runs inside `outcome.complete`; when it loses (or the report write fails, `ompFail`), the supervisor has already written its rows, so a run that sent nothing can carry a parse `refuse` row — exactly as it carries its `recordChatTurn` row today. Decision 5 offers the alternative (write after `won`).
- **Send (E11).** The delivery is not inside any turn. Its rows carry the outbox row's `run_id` (null for a run-less notification; today only `final_report` rows carry attachments and every one has a run), `tool_call_id` null, and are written **once per delivery attempt that reached `sendAttachments`**: an attempt whose text failed writes none; a re-delivery after a crash re-checks and writes again (a row is an attempt, as `secret.redact`'s). The rows are decided per file at the branch and written **after the loop and after the follow-up line**, so no insert sits between a check and its upload (R6 §4.0's reason: the loop's later files are re-checked against the disk; an insert between them only widens the window between the open and the upload of the next one). Nothing in a send reads a budget clock.

**One read, one predicate.** Each consult records the answer today's code already computed and branched on: at parse, the same `inside && inside(realpath)` conjunction (§4.1); at send, the `checked` discriminant the loop already holds (`:69`). The rule maps that answer; it re-reads nothing. Each row is a synchronous insert (`busy_timeout` 5 s, `run-store.ts:1439`): at parse it delays `finishSuccess`'s return by at most that bound under lock contention (the turn deadline is already cleared, `clearTimers` at `:899`); at send it delays the next dispatch. The zero-difference claim is the R6 one: zero differences in what is decided, sent and in what order, on the differential's fixed clock; wall-clock cost ≤ one insert per row. No path, file name, size or text is stored (`rowOf` has no input column).

### 4.1 The parse predicate (E2), pure refactor in `src/omp/attachments.ts`
- `parseAttachments(text, workspace)` returns `{ text, attachments, refused }`: `refused` holds each marker's resolved absolute path for which today's `if` (`:16`) is false, in line order. `text` and `attachments` are byte-identical for every input; the `if` keeps its exact expression (one predicate: the refused list is its `else`). The existing callers ignore `refused` (`settleStateFor` reads `.attachments.length`; `delivered()`'s text parse reads `.text`).
- `delivered()` (`:1613–1618`) also returns `refused: [...new Set(used.flatMap((p) => parseAttachments(p.final, ws).refused))]`: per pass, deduped by absolute path, the same `used` set as the accepted list. A path refused in one pass and accepted in another cannot happen (same workspace, same predicate, one synchronous call), so the two sets are disjoint; a test pins it anyway. The second parse of the joined text (`:1617`) is not a consult: it feeds only the text.
- `Delivered` (`supervisor-settle.ts:90`) gains `refused: readonly string[]`; `finalAudit` and `cardContinuationFailed` ignore it. Because a Telegram workspace is per chat and every refused path is outside it, no refused path is ever sent, so nothing else reads `refused`.
- Reason granularity (Decision 3): one parse reason, `marker_outside`, recording the conjunction as the code computes it. Splitting it into lexical (`..`, an absolute path elsewhere) and link escape (a symlink inside the workspace pointing out) would need the conjunction evaluated in two halves — two reads of the same predicate, which the code does not do today. Recommended: one reason.

### 4.2 The send predicate (E11)
- **Input** `{ seam: "send"; check: AttachCheck }`, `AttachCheck = "ok" | Exclude<AttachmentRefusal, "send_failed">`, set from the loop's `checked` (`:69`): an object → `ok`; a string → that kind (`over_count` included; it is the code's answer for the sixth file onward).
- **One predicate, protected (Decision 4-A).** `readAttachment`'s body moves, unchanged, to a new leaf `src/notifications/attachment-check.ts` as `checkAttachment(path, deps): AttachmentRefusal | { bytes }` with `deps = { canUpload: boolean; workspace: string | undefined; beforeRecheck?: (p) => void }`; `MAX_ATTACHMENTS`, `MAX_ATTACHMENT_BYTES`, `AttachmentRefusal` and an exported `overCount(i)` (`i >= MAX_ATTACHMENTS`) move with it and are re-exported from the adapter so every import stays valid. The adapter's loop calls `overCount(i) ? "over_count" : checkAttachment(…)`. The leaf is added to `PROTECTED_FILES`. Its limit, stated (as R2's 3-A): it protects the predicate; the loop that applies it, the call that uploads and the follow-up line stay self-writable, pinned by an adapter test (a refused file is never passed to `sendDocument`; the sixth file is `over_count` without an open).
- `unsupported` (a client without `sendDocument`) is a refusal the code makes before any path check; production's `TelegramClient` implements `sendDocument` (`telegram-client.ts:281`), so it is reachable only from a test client. Kept as a reason (the code's answer), not special-cased.

### 4.3 `attach.path`
- `id: "attach.path"`, `version: 1`, `stage: "settle"`, `input: "tool"` (the paths are the planner's output and the files the planner wrote), **`locked: true`**, one rule rung `attach_check`, `armed: { rule: "on" }`, `outcomes: []`.
- **Input** `{ seam: "parse"; check: "accepted" | "marker_outside" } | { seam: "send"; check: AttachCheck }`.
- **Rule:** `check` is `accepted` or `ok` → `send` / `parsed` (parse) or `checked` (send); else `refuse` / the check. (`parsed`/`checked` are written only under Decision 1-B.)
- **Verdicts** `send | refuse`; `defaultVerdict: "send"`; **`fail: "refuse"`** (a locked gate fails toward caution in its record: `fetch.ssrf` `blocked`, `secret.redact` `masked`). A thrown rule writes a `refuse` row at rung `fail` while the raw code goes on as today: read `rung` first (rule 1.2).
- **`reasonCodes`:** `marker_outside` (parse); `over_count`, `outside_workspace`, `not_a_file`, `too_large`, `linked`, `changed`, `unreadable`, `unsupported` (send); `parsed`, `checked` (1-B only). No path, file name or size is a reason code.
- **Effects:** `send` `none`; `refuse` `tighten`, reversible true (Paco can ask again; the file stays in the workspace), announced `none`, what "the file is not sent: at send, one '⚠ Not attached: <name> (<why>)' line follows the reply as today; at parse, the marker is dropped silently as today". `entryProblems` passes: a rule-only entry, a `tighten` verdict over `tool` input.
- **Consulted:** parse — once per distinct marker path (the accepted list, then the refused list) in `finishSuccess`, after `recordChatTurn` (`:1632`), for the parent run only (a merged run has `attachments: []` and no `delivered`); send — once per path in the payload's array per attempt that reached `sendAttachments`.
- **Rows:** Decision 1. Row order on a run (1-A): `secret.redact` (inside `enqueueFinalReportNotification`, within `outcome.complete`), then the parse `refuse` rows; later, at delivery, the send `refuse` rows in array order.

### 4.4 Recorder seams

### 4.5 Failure behaviour (R1–R6 carried over)
(a) The insert fails → `decision_record_failed` and one operator alert. At send that alert is enqueued into the outbox mid-dispatch and goes out on the next cycle; an alert carries no attachments, so it cannot consult `attach.path` (no self-amplification). (b) A recorder that throws past itself → logged. (c) A rule that throws → a `refuse` row at rung `fail` (≠ default, so written under either Decision 1 option); three in an hour page `decision_fallback`. None of the three changes which file is sent, the follow-up line, the outbox state or the run. The corpus carries one planted-throw item per seam.

## 10. Risks
- **The `readAttachment` move (4-A).** A slip changes which file is uploaded. The body moves verbatim; the differential compares the uploaded bytes' sha against the merge base on every send item, the `changed` item pins the open/re-check order, and the FIFO item pins `O_NONBLOCK`.
- **A recorder throw re-sending the text.** The adapter's `send()` throwing after the text went out marks the row failed and the dispatcher sends the text again. The `try` around `decideSync` in `recordChecks` is the guard; the fault items require `delivered` and one text send.
- **`run_id` on the dispatch record.** A new field on an interface every adapter receives; `LocalNotificationAdapter` and test adapters ignore it. A test pins that a run-less notification gets `null`, not `undefined`.
- **Unknown refusal volume.** Neither seam leaves a trace today (§3), so the row rate is unmeasured. Bounded by markers: 2 attachments delivered in 5 weeks; 1-A writes only refusals.
- **The parse residual (Decision 5).** A run whose `finishRun` loses after `finishSuccess` keeps its parse rows. Rare (the CAS loses only to a run already terminal or claimed elsewhere); the same exposure as `recordChatTurn`.
- **Tally churn.** Small under 1-A (refusal items only); the first task measures, never assumes.
