## 4. The entry

### 4.0 The recording rule (ADR 0034 §3.2, adapted to the settle stage and to delivery)
`attach.path` is the first entry consulted **after** the turn's end signal. R5/R6's guards (`!turn.endSignalled`, `!i.signal.aborted`) cannot be its liveness rule (§3). **Rows describe each observed check, not a file's final fate**: one path can be accepted at parse and refused at send (the file swapped, grown or removed between the reply and the delivery), and both rows stand. The rule this slice states, and the ADR 3.2 sentence it drafts (Decision 2):

- **Parse (E2).** "Live" at the settle stage means the turn took `settle()`'s success arm: `!turn.failure` at `:906`. A failed, aborted, killed or crashed turn takes `finishFailure` and is never consulted (a `/kill` during the snapshot sets `t.failure ??=` first, `abortTurn` `:1592`). Rows are written in `finishSuccess` on the consulting `Turn` passed in (never `this.turn`), `run_id` = `t.req.run_id`, `tool_call_id` null, **after `outcome.complete` and before `recordChatTurn`**, inside their own `try` that logs (§4.4). They are **best-effort terminal records**: written when the supervisor reached its success arm, whatever happens to the run afterwards. The one testable meaning (W1): *a turn whose supervisor reached the success arm has its parse rows even when `ompComplete` then fails to stage the report (`ompFail` `report_write_failed`) or loses the `finishRun` claim; a turn that took `finishFailure` has none.* (`recordChatTurn` has the same exposure today.) If `outcome.complete` itself throws, `finishSuccess` throws before the consult and no row is written — the same best-effort meaning, stated. Decision 5 offers the alternative (write after `won`).
- **Send (E11).** The delivery is not inside any turn. The adapter decides nothing new: it returns the checks it already made, `attach_checks` (closed enums, no path), on its `NotificationSendResult`. The **dispatcher** consults `attach.path` **after `markDelivered` committed** (`notification-dispatcher.ts:53`), next to `afterDelivered`, with the claimed row's `run_id` (null for a run-less notification; today only `final_report` rows carry attachments, all with a run), `tool_call_id` null. So no insert runs while the row is `sending`: recording can neither outlast the 30 s lease nor make a second sender re-send (codex B1). Rows are per delivery attempt that reached `sendAttachments` **and was marked delivered**: an attempt whose text failed returns no result; a crash between `markDelivered` and the consult loses that delivery's rows (stated residual: the reply went out; the row is a record, not a gate).
- **Bounded.** At most six consults per delivery: one per path among the first five, and **one** consult for the whole overflow (`over_count`, however many paths sit past the fifth — the code's one predicate `i >= MAX_ATTACHMENTS` answered for the rest). At parse, one per distinct marker path; markers are uncapped there, but a refused one costs one insert on a turn already ended and with its timers cleared (`:899`). Each row is a synchronous insert (`busy_timeout` 5 s, `run-store.ts:1439`): at send the worst case delays the **next** dispatch by six such waits, never the delivered one.

**One read, one predicate.** Each consult records the answer today's code already computed and branched on: at parse, `parseAttachments`' containment conjunction (§4.1); at send, the `checked` discriminant the loop already holds (`:69`). The rule maps that answer; it re-reads nothing. The zero-difference claim is R6's: zero differences in what is decided, sent and in what order, on the differential's fixed clock; wall-clock cost ≤ one insert per row, after delivery. No path, file name, size or text is stored (`rowOf` has no input column; `attach_checks` holds enums only).

### 4.3 `attach.path`
- `id: "attach.path"`, `version: 1`, `stage: "settle"`, `input: "tool"` (the planner's output and the files it wrote), **`locked: true`**, one rule rung `attach_check`, `armed: { rule: "on" }`, `outcomes: []`.
- **Input** `{ seam: "parse"; check: "accepted" | "marker_outside" } | { seam: "send"; check: AttachCheck }`.
- **Rule:** `accepted` → `send` / `parsed`; `ok` → `send` / `checked`; else `refuse` / the check (`parsed`/`checked` are written only under 1-B).

- **Row order on a run (1-A):** `secret.redact` (inside `outcome.complete`), the parse `refuse` rows, then — at delivery, after `markDelivered` — the send `refuse` rows in path order.

### 4.4 Recorder seams
- **Supervisor.** The consult goes through a new private `recordSafe(entry, s, run_id)` beside `record()` (`planner-supervisor.ts:428–432`): `record()` in a `try` that logs `attach_path_record_failed` with a fixed code. `record()` alone does not catch, and `decideSync` throws on a non-rule rung before its recorder's own catch (`decide.ts:25–26`): a registry mistake would otherwise skip `recordChatTurn` and `routeEnd` and raise a turn-crash incident after the reply was queued (codex B2). ### 4.5 Failure behaviour (R1–R6 carried over)
(a) The insert fails → `decision_record_failed`, a log kind (`incident-route.ts:53`), so its notice is one `incident_log` change-log row, not a chat alert (codex re-check B2).
